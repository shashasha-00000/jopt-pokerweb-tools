# 領収書の宛名修正（期別Sheetのまま運用）

対象ソース: `apps-script/ReceiptSemiAutoExperimental.gs`。
各期の既存Sheetを使う。統合管理表や他のSheetへの自動検索は追加しない。

## 更新後の初回操作

Apps Scriptに更新版を反映した後、「領収書 半自動 EXP → 初期設定」を1回実行する。
既存データを残して、GAME ID CHECK・領収書CHECKの末尾に「申請指示」、領収書管理の末尾に「生成データJSON」「生成日時」「元PDF_FILE_ID」を追加する。
追加予定列に独自の表頭やデータがあれば停止する。移動や削除は自動で行わない。

Form回答の「処理終了」下拉は以下の4種類になる。

| 値 | 意味 |
| --- | --- |
| 自動 | 通常の申請処理 |
| 完了 | 読み込み対象外 |
| 重複 | 読み込み対象外 |
| 修正 | 既存領収書の宛名修正。支払と旧番号の一致が必須。新規採番しない |

## 古い記録：支払明細を再取得して修正

1. 旧番号・PDFが「RSE_領収書管理」に残っている元のSheetを使う。
2. Formの対象回答に新宛名を入れ、「処理終了」を「修正」にする。既存の完了回答を再利用できる。重複した有効回答は作らない。
3. メニュー1で更新し、GAME ID CHECKの「確定宛名」と対象範囲を確認。確認OKを勾選してメニュー2。
4. 必要な支払明細を再取得してPW TSV表に置き、メニュー4。既存の進行中バッチを上書きしない。
5. 領収書CHECKの対象行が「差替」、新宛名、旧番号になっていることを確認。確認OKを勾選してメニュー5。
6. メニュー7でPDF生成。修正行にメニュー6の新規採番は適用されない。
7. PDFを確認して手動補送するか、従来どおりメニュー8で草稿、送信OK確認後に9で送信する。

旧記録なし、複数の旧番号、番号不一致はCHECKで止まる。新規発行へ自動的に切り替えない。
同じ宛名ですでに送信済みなら従来どおり重複除外になる。
対象範囲内の支払ごとに処理するため、一枚だけ修正する場合はPW TSV・CHECKの対象を確認する。
メニュー7は他の確定済み未生成行も処理する。マウス選択だけでは対象を限定しない。
修正経路では旧PDFを削除しない。旧草稿が残っている場合は誤送信しないよう確認する。
手動補送は自動送信扱いにならないため、管理表に送信日時・送信先・statusを記録し、対応したForm回答を「完了」にする。

## 今後の記録：管理表から一枚だけ修正

1. 「RSE_領収書管理」で現在有効な記録を1行だけ選択する。
2. メニュー **7d. 管理表の選択行から宛名修正PDF** を実行する。
3. 新宛名を入力し、確認画面の旧番号・大会・領収日・金額・宛名を確認して実行する。
4. 表示された新PDFを確認し、手動で補送する。Gmail草稿作成・メール送信は行わない。
5. 新管理行のstatusを「送信済み」にし、「メール送信日時」「送信先」に実績を記録する。

TSVやGAME ID CHECKが空でも利用できる。同じ支払が領収書CHECKで未送信の処理中なら停止する。
旧番号・元の支払年月日・金額内訳・税額・USDT換算額/レートを維持し、宛名だけ変更する。
新PDFと新しい管理行を追加し、旧行を「差替済み」にする。旧スナップショットと旧PDFは保管する。
直前版のPDF IDを「元PDF_FILE_ID」に記録する。

## 保底記録の範囲

今後、サーバーで新しくPDFを生成したときに、実際に使用したデータ・表示金額・税額・適用レート・発行者情報を「生成データJSON」へ保存する。
生成日時はAsia/Tokyo。JSONは通常編集不要。
過去のPDFを再利用・再登録しただけの場合は、当時の内容を確認できないためスナップショットを埋めない。
スナップショットがない旧行、破損したデータ、手編集で番号等が不一致になった記録は7dで再発行せず、再取得の経路へ案内する。
PDFのレイアウトは実行時のテンプレートを使う。保存するのは生成内容であり、旧テンプレートそのものではない。
