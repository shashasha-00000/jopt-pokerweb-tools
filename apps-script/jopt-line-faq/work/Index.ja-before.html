JOPTお客様対応窓口

裏側で起きること

左のボタンを押すと、選んだ項目の種類（回答・LINE誘導・担当者対応）と、Harness・Slackで行われる処理がここに表示されます。

    誘導先LINE

    ほかの公式LINEへ案内するときのリンクはここで一元管理します。リンクが変わったら、ここを1か所直せば全メニューに反映されます。

    担当者対応の種類

    担当者につなぐときの優先度、Slackの通知先、お客様に最初に聞く項目を種類ごとに決めます。

    開催回の変数

    回答文の中の {{event_name}} などに入る値です。開催回が変わるたびに、ここだけ更新します。有効期限を過ぎた値は赤で表示されます。

    共通メッセージ

    この設計は、2025年6月〜2026年10月のトーク履歴（会話2,630件、お客様メッセージ約10,000件）、同僚が作成した回答例141件、LINE Harness（v0.13.2）のソースコードをもとにしています。

    1. 基本方針

    • v1はボタン選択式です。お客様がボタンを順に選ぶと、データベースに登録済みの文面だけを返します。AIによる文章生成はしません。
    • すべての項目を3種類に分けます。回答（その場で解決）／LINE誘導（担当窓口が別）／担当者対応（個別の確認が必要）。
    • 担当者につなぐ前に、確認に必要な情報（GameIDなど）をお客様に先に送ってもらいます。今は担当者が「GameIDを教えてください」と聞き返すやり取りが返信の約2割を占めています。
    • 開催回ごとに変わる情報（フォームURL・年齢制限・日程）は変数として分け、本文を書き換えなくても更新できるようにします。

    2. 3つのルートと想定割合

    回答

    –

    支払い方法、年齢制限、チケットの使い方、領収書フォームなど。回答後に「解決した／担当者に相談」を表示します。

    LINE誘導

    –

    コイン残高（ポーカーギルド）、JOPT選手契約、JOPT Games、GameID、店舗様、ディーラー。過去12か月の約13%がこのルートです。

    担当者対応

    –

    プライズ未付与、誤送金、忘れ物、事前申込の確認など。Slackへ通知し、Harnessの未対応一覧に優先度つきで並べます。

    過去12か月の会話2,382件を、キーワードでこのメニューに当てはめた粗い試算です。LINE誘導だけで完結するのが約13%、回答を先に見せられるのが約60%（うち「プライズが届かない」など、最終的に担当者の確認が必要なものも含みます）、最初から担当者対応が約10%、キーワードで判定できない自由入力が約18%でした。v1では、自由入力にもメニューを返して選んでもらいます。

    4. 担当者への通知（Slack）

    1. 案件の作成：お客様が担当者対応の項目を押すと、ボットが確認項目の一覧を返信し、faq_tickets に案件を1件作ります。Harnessのチャットは「未対応（unread）」にし、メモに [要対応] プライズ未付与／高 のように書き込み、タグ「要対応/プライズ」を付けます。
    2. Slackへの通知：Slackアプリのボットトークン（chat.postMessage）で、優先度「高」は #cs-line-urgent、それ以外は #cs-line に投稿します。Harnessのチャット画面へのリンクを付けます。
    3. 情報の追記：案件作成から30分以内にお客様が送った内容（GameID、スクリーンショットの有無など）は、同じSlack投稿のスレッドに追記します。
    4. 営業時間外：お客様には「翌営業日以降の返信」と案内します。Slackへは🌙を付けて投稿し、メンションはしません。営業日の10:00に、未対応の案件をまとめて1回投稿します。
    5. 放置の防止：営業時間内に目標時間（高＝2時間、中＝当日中、低＝2営業日）を過ぎてもHarnessで未対応のままなら、スレッドで当番にメンションします。
    6. 状態の同期：担当者がHarnessから返信するとチャットは「対応中」になり、Slack投稿を「対応中」に更新します。Harnessで「解決済み」にすると、Slack投稿に✅を付けます。

    5. LINE Harness への組み込み

    Harnessは自社でデプロイしたものを改修できる前提です。FAQのテーブルは同じD1データベースに置き、ボットの返信もHarnessのトーク履歴に残るようにします。

    • apps/worker/src/routes/webhook.ts：postbackの処理で、data が faq: で始まるものを新しい services/faq-router.ts に渡します。ボタンは postback（表示テキスト＝ボタン名）で作るので、トーク画面にはお客様が押したボタン名が表示されます。
    • テキストメッセージで既存の自動応答に一致しなかった場合は、faq-router がメニューを返します。対応中の案件があるお客様には返信せず、今まで通り未対応一覧に入れます。
    • 返信は replyToken を使う replyMessage（無料・送信数の上限に数えられない）で送り、messages_log に source='faq_bot' で記録します。
    • scheduled.ts（cron）に、目標時間を過ぎた案件の再通知、10:00のまとめ投稿、チャットの状態とSlack投稿の同期を追加します。
    • リッチメニューに「お問い合わせ」ボタン（postback faq:node=root）を置きます。
    -- D1 に追加するテーブル（このページの「書き出し」でデータ入りのSQLを出力できます）
CREATE TABLE faq_nodes (
  id TEXT PRIMARY KEY, parent_id TEXT, sort_order INTEGER NOT NULL DEFAULT 0,
  label TEXT NOT NULL,                       -- ボタン名（20文字以内）
  type TEXT NOT NULL CHECK (type IN ('menu','answer','redirect','handoff')),
  body TEXT, channel_id TEXT, handoff_id TEXT, follow INTEGER NOT NULL DEFAULT 0,
  status TEXT NOT NULL DEFAULT '確認済', review TEXT, evidence TEXT,
  is_active INTEGER NOT NULL DEFAULT 1, updated_at TEXT);
CREATE TABLE faq_channels (id TEXT PRIMARY KEY, name TEXT, url TEXT, scope TEXT, status TEXT, note TEXT);
CREATE TABLE faq_handoff_types (id TEXT PRIMARY KEY, name TEXT, team TEXT,
  priority TEXT CHECK (priority IN ('高','中','低')), slack_channel TEXT, sla TEXT,
  fields TEXT /* JSON配列 */, note TEXT);
CREATE TABLE faq_vars (key TEXT PRIMARY KEY, value TEXT, valid_until TEXT, note TEXT);
CREATE TABLE faq_messages (id TEXT PRIMARY KEY, title TEXT, text TEXT);
CREATE TABLE faq_tickets (
  id TEXT PRIMARY KEY, friend_id TEXT NOT NULL, node_id TEXT, handoff_id TEXT,
  priority TEXT, status TEXT CHECK (status IN ('open','notified','in_progress','resolved')),
  collected TEXT, slack_channel TEXT, slack_ts TEXT,
  created_at TEXT, notified_at TEXT, first_reply_at TEXT, resolved_at TEXT);
CREATE TABLE faq_events (          -- 改善用ログ：どのボタンが押され、どこで担当者へ流れたか
  id TEXT PRIMARY KEY, friend_id TEXT, node_id TEXT,
  action TEXT CHECK (action IN ('tap','freetext','resolved','handoff')), created_at TEXT);

    6. 進め方

    1. 内容の確定（Harnessの改修と並行）：「要確認」の項目を担当者が確認し、誘導先LINEのリンクを確定します。現在の要確認は – 件です。
    2. テスト用アカウントで検証：社内メンバーだけが友だちのテスト用LINEで、全項目を押して確認します。
    3. 本番公開：営業時間内に公開し、最初の1週間はSlack通知と未対応一覧を重点的に見ます。
    4. 毎週の見直し：faq_events から「担当者に相談」が多い回答、よく来る自由入力を確認し、項目を追加・修正します。
    5. v2（Dify連携）：自由入力をDifyで分類し、項目のIDだけを返してもらいます。返信する文面は引き続きこのデータベースから取るので、AIが勝手な案内をすることはありません。

    7. 見る指標

    • 自己解決率：回答を見たあと「解決した」を押した割合
    • 担当者対応率と、種類ごとの件数
    • 初回返信までの時間（faq_tickets.first_reply_at）
    • メニュー未選択率：自由入力のあと、どのボタンも押されなかった割合
